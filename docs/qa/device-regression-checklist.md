## 一、先说结论要看哪一条

自续签（Seal 更新自己）的完整轨迹应该是这样，**顺序不能乱**：

```
安装      开始自替换安装：…，第 1/3 次，等待上限 N 秒
安装      自替换安装仍在等待：已等待 15 秒（installd 安装阶段不回报进度）   ← 心跳，每 15 秒一条
Seal 自替换：上传完成，1.2 秒后判断前台状态并回主屏
├─ 你还在看 App：
│    Seal 自替换：触发回主屏转场（suspend）
└─ 你已经切走了：
     Seal 自替换：当前在后台，等待回到前台再触发转场（最多 8 秒）
     ├─ 你回到 App ⇒ Seal 自替换：触发回主屏转场（suspend）
     └─ 你没回来   ⇒ Seal 自替换：在后台等待 8 秒仍未回到前台，强制 exit(0) 让 iOS 完成替换
安装      自替换安装调用已返回：…                                        ← 关键：这条有没有？
```

**只看最后一条在不在，以及它相对「触发转场」的先后**：

| 观察到的现象                                    | 结论                      | 下一步                                                              |
| ----------------------------------------- | ----------------------- | ---------------------------------------------------------------- |
| 「触发转场」或「强制 exit(0)」**出现过**，Seal 随后重新打开是新版 | 修复生效                    | 完成                                                               |
| 「触发转场」出现过，但 `自替换安装调用已返回` **永不出现**         | 转场（`suspend`）确实截断了安装链路  | 把转场触发点从「进入安装阶段」推迟到「安装调用返回之后」，或改为只 `exit(0)` 不 `suspend`（需真机 A/B） |
| `自替换安装调用已返回` 出现在「触发转场」**之前**              | 安装本身没问题，卡在回主页那一步        | 查前台状态判定                                                          |
| 心跳有，但**从头到尾没有**「上传完成」                     | 没走到转场那一步，卡在上传或 installd | 看心跳间隔是否稳定，判断进程是否还活着                                              |
| 一条心跳都没有，日志停在「开始自替换安装」                     | 进程被挂起了（不是 installd 卡住）  | 同上，查转场时机                                                         |
| **仍然卡在 93%，且日志里没有任何「Seal 自替换：」行**         | 「回主页」这段压根没被调用           | 把日志发回来 —— 这条本身是新信息                                               |

> **为什么之前认定是「后台分支」**：2026-09-16 的两份真机日志（各含两次自续签）显示，  
> 安装起点之后进程**既不转场也不退出**、照常写后台日志。  
> 而 `.triggerTransition` 必然调 `suspend`（生效则进程冻结、日志停），  
> `.waitForForeground` 超时必然 `exit(0)`（进程终止）—— 两者都没发生，  
> 只剩「`.standDown` 分支直接放弃」这一种解释。详见 QA 文档 §2.3.1。

## 二、逐项验收

### 1. 批量续签：抽屉里有百分比

- **怎么做**：选 2 个以上 App（含一个较大的）批量续签，打开运行中的抽屉。
- **看什么**：某项应该显示**上传百分比**（不是只有一个「传输中」的黑盒）。
- **通过标准**：上传完成的那一刻，该项从「传输中」**立即**变成「安装中」，并出现  
  「设备正在安装，此阶段没有进度回报 · 已等待 m:ss」，秒数在跳。

### 2. 单签续签：93% 之后不是一片空白

- **怎么做**：单个 App 续签，等它走到 93%。
- **看什么**：93% 处应该有等待说明（同上那句「已等待 m:ss」），而不是静止不动什么字都没有。
- **通过标准**：说明文字存在且秒数在走。

### 3. 运行中点「取消」

- **怎么做**：续签进行中，点「取消」/「取消续签」。
- **通过标准**：
  - 界面**立即**关闭；
  - 日志出现 `SEAL-SIGN-012`（单签）或 `SEAL-RENEW-011`（批量）；
  - 列表刷新后能看到真实结果（**不是**假装成功）。

### 4. Seal 自续签：拉下控制中心之后仍能完成替换

- **怎么做**：Seal 自续签，进入安装阶段后下拉控制中心（让 App 变成 `.inactive`），再回来。
- **通过标准**：替换正常完成，**不再停在 93%**。
- **这条是历史缺陷**：早先的实现遇到 `.inactive` 就早退，导致永远不触发替换。

### 5. 批量续签普通 App：不再长时间停在「传输中」

- **怎么做**：批量续签若干普通 App（**不含 Seal**）。
- **通过标准**：没有哪一项长时间停在「传输中」不动。

### 6. Seal 自续签：进入安装阶段后关掉抽屉，仍能完成替换

- **怎么做**：Seal 自续签，进入安装阶段（93%）后点「取消」关掉抽屉。
- **通过标准**：Seal **仍能完成替换**。
- **为什么**：触发点已经搬到状态层，不再挂在会被关闭的界面上。这条正是上一轮补修的缺陷。

### 7. Seal 自续签：日志里能看到完整轨迹 ★

- **怎么做**：Seal 自续签，无论成功失败，导出日志。
- **看什么**：对照本文「一、先说结论要看哪一条」那段轨迹。
- **通过标准**：无论成功（`自替换安装调用已返回`）还是有界失败（`自替换安装等待超时`），  
  日志都能指出卡在哪一段（上传 / installd / 回主页转场）。

### 8. Seal 自续签：切到后台后仍能完成替换 ★★

**这是本轮修复的主验证项。**

- **怎么做**：Seal 自续签，进入安装阶段（93%）后**把 App 切到后台**（按 Home / 上滑回主屏），  
  等几秒再回来看。
- **通过标准**：日志里出现  
  `Seal 自替换：当前在后台，等待回到前台再触发转场（最多 8 秒）`，  
  随后 8 秒内出现 `触发回主屏转场（suspend）` **或** `在后台等待 8 秒仍未回到前台，强制 exit(0)…`；  
  Seal 重新打开时已是新版。
- **修复前这条路径是「什么都不做」** —— 进程既不转场也不退出、永久占着前台，  
  iOS 永远等不到替换时机，界面就一直停在 93%（这就是你遇到的那个「怎么都没反应」）。
- **如果仍然卡住**：把 `Seal-log.txt` 发回来。日志里现在有完整的判定依据。

### 9. 描述文件清理：维护期这条路径到底跑没跑 ★

**问题 5 的复查项。** 2026-09-17 复查时发现：维护期清理（`AppMaintenanceJob` 第 4 步）  
在用户的设备上**一次都没跑过** —— 但原因不是它坏了，而是**它不在用户那个构建里**  
（第 4 步是 run#79 `bc069e3` 才加的，用户的构建 ≤ run#75）。  
另一个坑是：`.skipped` 原先只有一句 `break`、`.failed` 只弹窗，**都不写日志**，  
所以「这一轮到底跑没跑」无法回答。本轮已补齐。

- **怎么做**：打开 Seal，静置 30 秒以上（让空闲维护有机会跑），然后导出日志。
- **看什么**：搜 `描述文件清理`。应该出现**恰好一条**下列结果之一：

| 日志                                                     | 含义              | 下一步                                                                |
| ------------------------------------------------------ | --------------- | ------------------------------------------------------------------ |
| `设备端旧描述文件清理：描述文件清理：扫描 N，匹配 M，删除 K`（`SEAL-PROFILE-320`） | 第 4 步跑了         | 看 `K`：> 0 说明回收生效。`匹配 M` 是「当前在用的 Bundle ID 里，设备上确实有 profile 的个数」——你设备上有 10 来个 App、多数带扩展，所以 **M 应该在 20 上下**；若只有 `匹配 1`，说明装的还是 run#75 之前那个 keep-map 只有单条的旧包 |
| `维护作业本轮跳过：有前台操作正在进行`（`SEAL-STORAGE-009`）               | 有前台操作，本轮被抢占     | 静置重试；若**长期只有这一条**，说明抢占过于频繁，需要把「跳过」改成「推迟」                           |
| `维护作业在「描述文件清理」阶段被打断`（`SEAL-STORAGE-006`）               | 跑到第 4 步时被用户操作打断 | 同上                                                                 |
| `维护作业失败：…`（`SEAL-STORAGE-010`）                         | 维护整轮失败          | 把日志发回来                                                             |
| **一条都没有**                                              | 维护压根没被调用        | 把日志发回来                                                             |

- **注意 `dump 尝试 N 次`**：出现这个后缀说明前几次撞上了设备不可达（`NoDevice`）。  
  单次 `NoDevice` 不再等于整轮白丢 —— 现在会自动重试 3 次（每次间隔 4 秒并重置 provider）。
- **两个数字能反过来验证堆积速度**：`扫描 N` 是设备上的 profile 总数。  
  历史上它出现过 325（09-15）→ 23（09-16）的跳变，原因不明；这次记一下前后值。
  其中**大部分是「旧 Team 后缀」的 profile** —— 本轮起会开始回收，见第 11 项。
  别把「N 一次没降多少」当成清理失败：每轮只处理当时能确认「设备上确实没装」的候选，
  而且「同一 App 用两个 Team 各装一份」的那些会**故意保留**。
- **提醒（这一条我们自己也踩过两次）**：看到「某个日志码零命中」时，  
  **先确认那个字符串在你分析的那个构建里存在**（`git show <sha>:<file> | grep <码>`）。  
  run#73 / run#75 里根本没有 `SEAL-PROFILE-320`，所以它的零命中是**平凡结论** ——  
  拿它去论证「路径没执行」会得出错误结论。

### 10. Seal 自续签后：旧 profile 被回收 ★

**问题 5 的另一个复查项。** Seal 的自更新不走普通安装，所以「安装后旧描述文件清理」  
轮不到它 —— 回收 Seal 自己那 16 份堆积**只能**靠自替换结算路径，  
而这条路径原先只把摘要写进事务审计、不写日志。

- **怎么做**：完成一次 Seal 自续签（替换成功、Seal 重新打开是新版），导出日志。
- **看什么**：应出现 `自替换结算清理：描述文件清理：扫描 N，匹配 M，删除 K`（`SEAL-PROFILE-322`）。
- **通过标准**：
  - `删除 K` > 0，且
  - `匹配 M` 为 1（**这条路径只锚定一个 Bundle ID**，见下），且
  - 打开 StikDebug 的 App Expiry 页，**Seal 当前那个 Bundle ID 的那一组**应降到 1 份。
- ⚠️ **不要期待「Seal 那一组从 17 份降到 1 份」** —— 上一轮这里写错了。  
  结算清理调的是 `removeStaleProfiles(for: bundleIdentifier, keeping:)`，**只覆盖 Seal 当前那一个
  Bundle ID**。而你的设备上 Seal 有 **5 个 Team 变体**
  （`com.mjorb.seal.` + `49778Q7UWQ` / `6T43967CCT` / `CT8QZ7352B` / `KYRJV2U7WS` / `TB95F327DS`），  
  另外 4 个变体的 profile **不会被这条路径碰到**。所以 Seal 那一组会从 ~17 降到 ~5 左右，
  **不是 1**。剩下那 4 个变体属于「旧 Team 后缀」问题，见下面第 11 项。
- **若出现 `中断于 skipped-identity-changed`**：说明结算时读到的运行身份与事务记录不一致，  
  整批放弃（这是**有意的保守**，删错一份 Seal 立刻无法启动）。把日志发回来，需要单独分析。
- **若出现 `中断于 dump`**：看有没有 `dump 尝试 3 次`。有 ⇒ 隧道/RSD 一直连不上（环境问题）；  
  没有 ⇒ 单次失败，属于瞬时抖动。

### 11. 旧 Team 后缀的 profile：现在会回收了 ★
2026-09-17 用 19 份日志里所有 `.seal.<后缀>` 形态统计：**19 个 base × 13 个 Team = 39 个
Seal 生成过的 Bundle ID**（详见 QA 文档 §7.8）。原因是你在用多个 Apple ID 轮换突破
免费账号「3 个自签应用」上限，每换一个账号 Seal 就给每个 App 生成一个新的 Bundle ID。

**这一轮实现了回收**（判据见 QA 文档 §7.9）。删除条件三条同时成立：
①不在当前 keep-map；②形态含 `.seal.` 中缀；③设备端核验确认**没装**。

> 🔧 **run#106 起：Seal 早期的「裸」Bundle ID `com.mjorb.seal` 也会被回收。**
> 它不含 `.seal.` 中缀，旧实现下**永远清不掉** —— 你截图里那两份都叫「Seal」的
> profile 就是它（一份在用、一份是遗留）。留着它的实际危害是**你手动清理时会删错**
> 正在用的那一份。安全性由两道既有防线保证：keep-map 优先，且仍要过设备端核验
> （那个旧 App 若还装着就保留）。

⚠️ **2026-09-17 首次真机验证时发现一个会删数据的缺口，已修**：`isAppInstalled` 对
**扩展** Bundle ID 恒为 `false`（扩展不是独立安装的 App，`installation_proxy` 里没有它），
所以第 ③ 条对扩展**完全没有保护作用** —— 真机上 `自替换结算清理` 把 LiveContainer 的
三个扩展 profile 删了（`候选 4，回收 3，已装保留 1`，主 App 保住了、扩展没保住）。
现在把两个集合拆开：**严格集合**决定留哪份（只收有可信 UUID 的），
**宽松集合**决定不删谁（记录里出现过的所有 Bundle ID，**含扩展**，不看安装状态）。
**受保护集合为空时整轮不回收**（记录读不到 ⇒ 保护范围未知 ⇒ 宁可不删）。

**本轮新增的验收点**：走完一次 Seal 自续签后，`自替换结算清理` 那一条里
**不应该再出现任何已装 App（含它的扩展）的 Bundle ID**。如果出现 `回收 K > 0`
且示例里有你**正在用**的 App 的扩展，把日志发回来 —— 那说明保护集合又漏了。

- **怎么做**：跟第 9 项同一份日志（打开 Seal 静置 30 秒以上再导出）。
- **看什么**：第 9 项那条 `设备端旧描述文件清理：…` 后面会多出一段：

  ```
  ；旧 Team 变体：候选 N，回收 K，已装保留 M，未能核验 U，扩展随父保留 E，受保护 P，示例 a.seal.X、b.seal.Y
  ```

| 字段 | 含义 | 怎么看 |
| --- | --- | --- |
| `候选 N` | 形态上像 Seal 生成的孤儿（本地筛出来的总量） | 你设备上应在 **30 上下** |
| `回收 K` | 真正删掉的份数 | **`K > 0` 就是生效了**；首次跑应该能删掉一批 |
| `已装保留 M` | 设备上确实装着对应 App，所以**故意不删** | 见下面的说明 —— `M > 0` 和 `M = 0` **都正常** |
| `扩展随父保留 E` | 它是**扩展**（自己不是独立 App），但**父 App 装着** ⇒ 保留 | `E > 0` 说明父 App 保护生效；这一项是 2026-09-17 新加的 |
| `受保护 P` | 本轮受保护集合（记录里出现过的 Bundle ID）的**规模** | **`P` 很小而 `候选 N` 很大** ⇒ 记录没读全（例如刚重装过 Seal），此时「候选多」不代表设备上真有那么多孤儿 |
| `未能核验 U` | 查询抛错 | 设计上只可能是 **0 或 1**（见下） |
| `回收中止：…` | 中止原因 | **出现它就一份都没删**（连已经问过的那几条也不删），见下 |

**`已装保留 M` 怎么读**：`M > 0` **不是漏删**，是保护生效。它只会在一种情况下出现 ——
某个 Bundle ID **形态上像 Seal 生成的、但不在保留集合里，而设备上确实装着**。
主要来源是该 App 还在设备上、却已从 Seal 的列表里删掉（或记录里没有可信的 profile UUID）。

⚠️ 别把它和「同一个 App 用两个 Team 各装一份」混起来：那种情况两个 ID **都在**
keep-map 里，走的是**保留集合内去重**那条逻辑，不体现在这个数上。

**`扩展随父保留 E` 怎么读**：扩展（`…ShareExtension` / `…LiveProcess` 这类）**不是独立安装的
App**，系统查询对它们**恒答「没装」**，所以设备端核验救不了它们 —— 只能靠「父 App 确实装着」
来保留。**看到 `E > 0` 说明这道防线生效了**；如果示例里出现了你正在用的 App 的扩展、
而 `回收 K > 0`，把日志发回来（那说明父 App 也没被认出来）。

- ⚠️ **`回收 0` 不是「形态没匹配上」**：四种情况都会导致 `回收 0`，靠上面几个数区分 ——
  `候选 0` = 形态没匹配；`已装保留 M` / `扩展随父保留 E` = 设备上真的都还装着；
  `回收中止` = 通道不可信。
- **看到 `回收中止：阳性对照未通过（com.mjorb.seal.xxx 被答成未安装）`**：  
  说明设备查询通道此刻不可信（连 Seal 自己都被答成「没装」），于是**整轮不删**。  
  这是**有意的保护** —— 没有它，「隧道抖动 ⇒ 所有候选都被读成没装 ⇒ 全删」的路径是敞开的。  
  静置重试即可；若长期如此，把日志发回来。
- **看到 `回收中止：核验通道不可信（…：查询失败）`**：同上，某次查询抛错就停止整轮。  
  抛错是**全局性**的（设备/隧道不可达），所以继续问剩下的候选没有意义。  
  ⚠️ 现在中止意味着**一份都没删**（连已经问过的那几条也不删）——
  半路删掉一部分再中止，等于用一条已判定不可信的通道做了一半不可逆的事。
- **`未能核验 U` 只可能是 0 或 1**：第一次查询失败就中止整轮。  
  如果你看到 `U` 是个大数，说明这个约束被改坏了，把日志发回来。
- **预期 `扫描 N` 会开始下降**，但**不会一次降到很低** —— 每轮维护只处理当时能确认的候选，
  而且 `已装保留` 的那些永远不删。记一下前后值。
- **另一条验收路径**：完成一次 Seal 自续签（替换成功），日志里会出现
  `自替换结算清理：… ；旧 Team 变体：…`（`SEAL-PROFILE-322`）。  
  这条路径是**唯一**能回收 Seal 自己那 5 个 Team 变体的地方 —— Seal 的自更新不走普通安装。

### 12. 新账号需要双重认证时，提示要指向「验证码」而不是「密码」★

**这一项修的是什么**：你新加的那个 Apple ID 报过

```
[SEAL-AUTH-107a] Apple ID 验证失败。
Code：3018
描述：This account requires signing in with two-factor authentication.
```

界面当时给的恢复建议是「**重试；如持续失败请核对 Apple ID 与密码**」—— 而**密码完全没问题**：
Apple 已经接受了密码，只是要求走第二步（输验证码）。这条错引导会让你在一个正确的密码上
反复试，甚至跑去重置密码。

**怎么验**：设置 → 添加 Apple ID → 用一个**会要求双重认证**的账号登录（就是上次报 3018 的那个）。

| 看到什么 | 说明 |
|---|---|
| 弹出「**输入验证码**」输入框 | ✅ 正常路径 —— 填入 Apple 发来的六位数字即可完成添加 |
| 没弹框、直接失败且文案是「**Apple ID 需要双重认证**」 | ✅ 分类生效（说明验证码这步被跳过了/超时了）；恢复建议应写「**重新添加账号，在弹出的「输入验证码」里填…**」，**不应**出现「核对 Apple ID 与密码」 |
| 失败文案仍是「Apple ID 验证失败 / 核对 Apple ID 与密码」 | ❌ 没修上，把日志发回来 |
| 失败文案变成「**连不上 Apple / 切换非国内梯子**」 | ❌ 3018 被限流分支吞了，把日志发回来 |

**日志里的判定码**：`SEAL-AUTH-101a` 才是「需要双重认证」这条；`SEAL-AUTH-107a` 是泛化的
「Apple ID 验证失败」。按 `SEAL-AUTH-101` 前缀扫能同时看到「验证码被拒（`-101`）」
与「验证码这步没走完（`-101a`）」。

**顺带自查一件事**：如果**没弹验证码框**就直接失败，除了上面这条，还要留意
`VerificationCodeBroker` 的 `allowsInteractivePrompt` —— 它设计上是「批量续签时关掉
交互式 2FA、之后恢复」，但目前生产代码里**没有任何地方调用 `setInteractivePromptAllowed`**，
所以它恒为 `true`。也就是说「没弹框」不可能是这个开关造成的；如果真遇到，是别的原因。

### 13. 安装卡住时，日志里应该有**心跳** ★

**这一项修的是什么**：你在 14:54 那次批量续签里，LiveContainer 卡在「正在安装 ·
已等待 9:04」，而导出的日志里从 `14:54:02 开始安装：…` 到导出那一刻**一行都没有** ——
「还在装」和「进程/通道死了」在日志上完全分不开。

根因：心跳只加在 **Seal 自替换**那条安装路径上，普通安装没有。

**怎么验**：随便装/续签一个 App。分两种情况：

| 看到什么 | 说明 |
|---|---|
| 安装很快完成（普通 App 约 **7–11 秒**），日志里只有「开始安装」+「安装调用已返回」 | ✅ 正常 —— 心跳间隔 15 秒，正常安装根本不会触发它 |
| 安装超过 15 秒时，日志里**每 15 秒**出现一条 `安装仍在等待：已等待 N 秒（installd 安装阶段不回报进度）` | ✅ 心跳生效 |
| 安装卡了很久，日志里仍然**一片空白** | ❌ 没修上，把日志发回来 |

⚠️ **心跳只证明「Seal 自己还活着」，不证明「安装还在推进」** —— 安装阶段 installd
**不回报任何进度**（这一点在自替换那条链路上早就写在注释里了）。所以心跳的用途是
**区分「界面卡住但进程正常」与「进程已经没了」**，以及给下次排查留下时间线。

🔍 **如果卡住，请顺手看一眼有没有这一条**（run#102 起新增的取证）：

```
安装前探测：复用已启动 N 秒的缓存会话，5 秒无响应（疑似死连接）
```

出现它 = **复用了一条已经死掉的设备连接**，这是「安装静默很久却什么都不报」的
头号嫌疑（同步调用在死连接上不会报错，只会阻塞到系统放弃）。把日志发回来即可，
**这一条就是决定下一步修法的证据**。正常安装不会出现这一行。

🔍 **等过「明显超常」时还会多一条**（run#105 起；run#110 起阈值改为按包大小算）：

```
安装等待已明显超常：已等待 N 秒（本次等待上限 M 秒；普通小包安装约 7–11 秒）。
判读：界面仍显示上传百分比 ⇒ 卡在传输；显示「设备正在安装」⇒ 卡在 installd
```

**它同时告诉我和你自己「卡在哪个阶段」** —— 请把**截图**一起发回来（界面在显示上传百分比
还是「设备正在安装」），这一条日志才有判读价值。

⚠️ **阈值不是固定的 2 分钟**：它取「本次等待上限的四分之一」——小包约 201 秒、
大包（抖音 779 MB 那种）约 600 秒。**大包本来就慢，等几分钟是正常的**，
别把这条当成失败信号。

**如果又卡住了**：等它自己走到上限（`等待上限 N 秒` 会写在「开始安装」那一行里，
普通 App 约 **804 秒 ≈ 13.4 分钟**，大包可到 2400 秒），或者手动取消。两种情况下日志里都该有心跳，
把日志发回来就能看出卡在第几秒、以及卡住前最后发生了什么。

⚠️ **超时之后会发生什么（2026-09-17 更正）**：

| | |
|---|---|
| 底层安装调用 | **不会被取消** —— 同步调用没有取消机制，它会在后台自己跑完 |
| 会不会自动重试 | **不会**。超时按「确定性拒绝」处理，直接抛错 |
| 所以 | **看到「安装超时」之后，先等 1–2 分钟回列表确认这个 App 是否其实已经装上**，别急着再点一次续签 |

> 旧文案写的是「超过 10 分钟仍未完成，**系统已自动重试**」—— 两句都是错的
> （实际不重试；上限也按包大小算）。已修。

### 14. 批量续签包含 Seal 自己时，重启后**不该**报「结果未知」★

**这一项修的是什么**：只要批量续签里含 Seal 自己，Seal 就必然要把自己替换掉 ——
而那一刻队列里 Seal 那一项还是「运行中」。旧实现在重启后把它**一律标成「结果未知」**，
于是同一个批次同时给出三份互相矛盾的结论：

```
批量续签结果抽屉已关闭（completed(total: 2, succeeded: 2, failed: 0))     ← 成功 2/2
上次续签被中断，1 个应用的结果未知，需要重新核验                          ← 假警报
（队列里还留着一个「永远待处理」的幽灵条目）
```

**根因**：那一项的结果**其实已经写进持久化载荷**了（Seal 自替换成功时进程已经死了，
没机会写自己的状态，所以写入侧替它记成 `completed`）。两条恢复机制各说各话。

> ⚠️ **修复在 run#104 及以后**。run#102/103 的包仍会报这条假警报（run#103 更是直接编译红，
> 别装）。

**怎么做**：做一次**包含 Seal 的批量续签**（≥2 个应用），等它自动重启，然后导日志。

**看什么**：

| 看到什么 | 说明 |
|---|---|
| `[SEAL-RENEW-026] 上次续签被中断，但 N 个应用的结果已从持久化载荷结算（不再标为未知）` | ✅ **新行为**：N 通常 = 1（Seal 自己） |
| `[SEAL-RENEW-007] … 个应用的结果未知，需要重新核验` | 只有在**真没结论**时才该出现。若它和「成功 2/2」同时出现 ⇒ ❌ 没修上 |
| `[SEAL-RENEW-021] 待恢复的批量续签结果被跳过` | 只该出现**一次**（真被跳过时）。反复出现 ⇒ ❌ 噪音回来了 |
| 结果抽屉 | 应显示 `succeeded` 等于实际成功数，且**列表里没有多余的待处理项** |

**注意**：`SEAL-RENEW-026` 是**正常路径**的留痕，不是错误 —— 它的作用是让「0 个未知」
这件事可归因（是本来就没被中断，还是被结果结算掉了）。

  - **有 1–4、没有 5** ⇒ 卡在循环之后的环节（配对匹配 / 安装服务就绪）；
  - **1–5 齐全** ⇒ 检测有结论，按第 5 条里的**首个错误码**定位 ✓。

**⏱️ 「验证中」要等多久**（2026-09-20 修）：

|---|---|---|---|
| **修复后**（构建 **186** 起） | 约 20–60 秒 | 待测（预期与名义同量级） | `probeDeviceFetchTimeoutMs` = **1 秒** ✓ |
| **184 及更早**（探测**挂住**：连接无响应、被外层 5 秒截断） | **约 3.4 分钟** | **12 分钟以上** ✗ | `deviceFetchTimeoutMs` = 15 秒 ✗ |
| **184 及更早**（探测**快速失败**：对端回 RST） | **约 20 秒** | **约 25 秒** ✓ 实测 | 同上（但没花到预算） |

> ⚠️ **「3.4 分钟 / 12 分钟」只属于「挂住」那一行** —— 别把它当 184 的固定表现。
> **实测证据（2026-09-20，构建 184 真机日志）**：同一台设备连续失败的时间戳是
> `21:30:02 → :27 → :52 → 21:31:23`，**间隔 25 秒** ⇒ 那是 `ready()` **立刻拿到 RST**、
> 每轮只付 0.5 秒睡眠的形态（36 × 0.5 s ＋ 固定开销）。
> ⇒ 判断「这轮为什么慢」要先看**底层错误是超时还是 RST**：
> `ConnectionRefused` ⇒ 快速失败（≈20–25 秒）；无底层错误 / 超时 ⇒ 挂住（≈3.4 分钟起）。

- 设备探测是 `for attempt in 0..<36`，每轮 = `readyDeviceIdentifier()` ＋ 500ms 睡眠
  （**设计意图 = 给 RSD 握手约 18 秒**）；`readyDeviceIdentifier()` = `isReady()` + `fetchUDIDDetailed()`。
- ⚠️ **等待与代价是两件事，必须分开算**（`BlockingCall` 明文：超时只表示「本次放弃等待」，
  底下同步 FFI 仍在后台跑完、结果被丢弃）：
  - **等待** = 「外层有界等待」与「内层预算」中的**较小者**。`isReady()` 外面套着
    `offThread(5 秒)`（`blockingCallTimeoutSeconds`）⇒ **修复前每轮只等 5 秒**，
    那 15 秒**从来没有延长过等待** ✗。
  - **代价** = 每轮**丢掉一个还在跑 15 秒的后台阻塞调用**，它一直占着 Swift 协作线程池的线程
    ⇒ 把后续 `Task.sleep` 与计时器的恢复一并推迟 ⇒ **实测 12 分钟以上**（≈ 每轮 20 秒）就是这么来的。
  - ⇒ **修复的关键那一刀是把被遗弃的阻塞调用从 15 秒缩到 1 秒**，不是那点算术。
- ⇒ **有外层重试的地方，内层预算必须短**（重试本身就是等待）：就绪探测用 1 秒，
  一次性路径（dump / 安装 / DDI / JIT）继续用 15 秒 ✓。守卫 **R61** 钉住四条判据
  （含「`ready()` 里便宜判据必须在 `getFirstDevice()` 之前」✓）。
- **耗时是逐项算出来的**（改之前先看这张表，别凭感觉估）：

  | 情形 | 每轮 | 36 轮 | ＋固定开销 | 名义合计 |
  |---|---|---|---|---|
  | **186 起**：隧道**没通**（便宜判据即为假 ⇒ 每轮 ~0 秒） | 0.5 s | 18 s | ~2 s | **~20 秒** |
  | **186 起**：隧道通了、只差设备（每轮 1 秒探测） | 1.5 s | 54 s | ~2 s | **~56 秒** |
  | **184 及更早**：`offThread(5 秒)` 在 5 秒处截断（内层 15 秒够不到） | 5.5 s | 198 s | ~2–7 s | **~3.4 分钟**（实测 12 分钟以上 ✗） |

  （固定开销 = `waitForNetworkRefresh` 0.5 s ＋ `probeTunnel` 1.8 s ＋ 首次探测 ＋ `Minimuxer.start` ≤4 s。）
- ⚠️ **「184 及更早」名义 ≈ 3.4 分钟、实测 12 分钟以上**，差额来自被遗弃的阻塞调用挤占线程池
  （见上）—— **不要把它归给「进程挂起」就算了**，那只是次要因素。
- ⚠️ `readyDeviceIdentifier()` 第一行是 `guard await isReady() else { return nil }` ⇒
  `ready()` 为假时 `fetchUDIDDetailed()` **根本不会被调用** ⇒ 每轮只付**一次**探测。

  第三版才读到 `isReady()` 外面那层 `offThread(5 秒)` ⇒ 名义 3.4 分钟 ✓。）
- ⚠️ lockdown 路径下 `ready()` 会**真的走到** `getFirstDevice()`，

## 三、只有某一个 App 签不上？先别急着重验证 Apple ID

**判据（用户 2026-09-17 反馈，也是最有用的一条）**：

> 同一个 Apple ID，**签其它 App 正常、只有某一个签不上** ⇒ **账号没坏**，别去反复重新验证。

**最常见的原因是「请求密度」**。多扩展 App 一次签名要**连续注册多个 App ID**
（抖音 = 主 App + 8 扩展 ⇒ **连发 9 次** `addAppID`），Apple 对短时密集请求会**掐断会话**，
返回的错误**看起来像登录失效，其实不是** —— 重新验证没有用。

⚠️ **「重新验证 → 再签 → 又被限流 → 又被要求验证」这个死循环**在代码注释里被明确记录过
（原话就是「无论怎样在验证 Apple ID 就报错失效」）。run#111 之前，**证书阶段**的文案
只给「去重新登录」这一条路，正是死循环的成因；现在改成了
**先等几分钟 → 仍失败再重新验证 → 或改用其它 Apple ID**。

⚠️ **名额是共享的，而且「谁的失败更致命」不一样**（run#114 起已修）：免费账号
「7 天内最多 10 个 App ID」是主 App 与扩展**共享**的名额；**扩展建号失败会被丢弃、继续签名，
主 App 建号失败则整个签名抛错**。抖音要 **9 个**（主 App 1 + 扩展 8），
所以它是唯一容易撞上限额的 App —— 这正是「只有抖音签不上」的原因之一。
（run#114 之前按 Bundle ID 字母序建号，`com.x.app-ext` 会排在 `com.x.app` 前面，
扩展先把名额吃掉、主 App 反而签不上，**名额还白花了**；现在主 App 一定先建。）

### ★ 2026-09-18 真机日志确认的一条判据（最有解释力）

对照同一份日志里**成功**与**失败**的签名，差别只有一个：

| 那次签名 | 名额诊断说的 | 结果 |
|---|---|---|
| Seal 自续签 | 本次需 1 个…**需新注册 0 个** | ✅ |
| LiveContainer | 本次需 4 个…**需新注册 0 个** | ✅ |
| 3105 | 本次需 1 个…**需新注册 0 个** | ✅ |
| **抖音** | （**根本没写出这行**） | ❌ |

⇒ **三次成功的一次 App ID 都没新建；抖音要新建 9 个。**
**差别不是证书、也不是扩展数量，而是「要不要新建 App ID」。**
账号被 Apple 限流后，App ID 都已注册好的 App 照样能签，要新建 9 个的就撞在第一个请求上。

⚠️ 抖音两次失败时**都没有** `App ID 名额` 那行 ⇒ 它**根本没走到建号**。
**所以「扩展把名额吃光」不是这两次的原因**（该账号当时只注册了 1 个 App ID，9 个新的完全放得下）。

### ★ 看到「正在准备应用文件」时不要慌（run#120 起）

抖音这种 **780 MB** 的包，Seal 要在本地做**解压 / 改写 Bundle 结构 / 重签所有二进制 / 重新打包**
（约 33 个 Mach-O、5053 个文件）—— 实测要 **112 秒**，界面会停在这一步不动。

**这一步完全不碰 Apple。** 所以：

- ❌ **不要**因为「卡住」就去重新验证 Apple ID；
- ✅ 耐心等 2–3 分钟（旧包会显示成「正在验证 Apple ID」，新包会显示「正在准备应用文件」）；
- ✅ 日志里会有一条 `签名：应用文件准备完成（解压/改写/重签/打包），耗时 N 秒`。

### ★ 千万别做的两件事（2026-09-18 用户实测踩到）

1. **别再反复「重新验证 Apple ID」**。日志证明登录是好的：同一个账号在 06:53 刚成功建过证书、
   并成功签了另一个 App。限流**不是**登录失效，重新验证解决不了它，只会再发一批请求、
   让限流更久。
2. **不要卸载重装那个 App**。卸载不解决限流，只会让你重跑一遍整个流程。

> 说明：构建 118 及更早，App 会把「限流」这条错误**显示成**「Apple ID 会话已过期 →
> 去「我的」重新验证」。那是被覆盖过的文案，不是真实原因（新构建起不再覆盖）。

### 正确的做法

1. **停手 15–30 分钟**：不签名、不重加账号、不进证书页。每次操作都在给限流续命。
2. **然后第一个就签抖音**（中间别插别的 App），让 9 个 App ID 一次建完。
3. 仍失败 ⇒ **换一个从没签过抖音的 Apple ID** ← 新账号没有限流历史，最有效的一招。
4. 再失败 ⇒ 发日志给我，看下面这几条判据。

**按这个顺序试**：

1. **先看日志里有没有这条**（run#114 起才有）：

   ```
   App ID 名额：本次需 9 个（主 App 1 + 扩展 8），账号上已有 N 个、其中可复用 M 个，需新注册 K 个
   ```

   ⚠️ **它用来「排除假设」，不是用来算「剩余名额」**：

   - **`K` = 0** ⇒ 本次一个 App ID 都不用新建 ⇒ **不可能**是「建号突发被限流」，去别处找原因。
   - **`K` 很大**（抖音通常是 9）⇒ 本次确实是一轮突发，限流假设成立。
   - ⚠️ **`N`（账号存活 App ID 数）不能用来算剩余名额** —— 上限是「**7 天内注册数的滑动窗口**」，
     不是「存活数 ≤ 10」。源码注释写得很清楚：窗口滚动后老 App ID 仍在存活列表里、
     却已不算进当周窗口，账号可以合法攒到 >10 个。**只有 Apple 的裁决说了算。**
   - ⇒ **「名额满」与「限流」的真正判据是失败时的日志码**（见下面第 5 / 6 步）：
     `SEAL-APPID-304` = 名额满（Apple 返回 1009/3013）；`SEAL-AUTH-107` = 限流（1100）。
     查 `docs/qa/log-code-index.md` 有全部码的索引。

   🔍 同一条日志里还应该看这两行（run#115 起）：

   ```
   Apple 会话疑似被限流，退避 2 秒后重试 创建 App ID com.xxx        ← 哪一步被限流，直接写出来了
   Apple 会话疑似被限流，退避 4 秒后重试 更新应用能力 com.xxx       ← updateFeatures（每个扩展都会走）
   ```

   - **看到退避行** ⇒ 限流确实发生了，而且**退避重试正在工作** —— 耐心等它跑完，
     不要手动重试（会叠加请求密度）。
   - **完全看不到退避行、却仍失败** ⇒ 不是限流，去看失败时的**日志码**（第 5 / 6 步）。
   - ⚠️ **最坏情况会等比较久**：抖音有 18 次写请求（9 个 App ID × 2 次），
     每次最多退避 3 轮（1.5+4+8 秒）⇒ 理论上可能多等几分钟，界面会一直停在
     「正在准备 App ID」。这是**有界**的，不是卡死。

2. **别重新验证**（除非反复失败多次）。
3. **换一个 Apple ID 签它** ← 最有效（新账号没有被限流的历史）。
4. **等几分钟，然后只签它**（中间别签别的应用）。
5. 若日志里出现 **`SEAL-APPID-304`** ⇒ 是「**7 天内最多注册 10 个 App ID**」的窗口满了
   —— 与限流是两回事，**只能等 7 天或换账号**（App ID 无法手动删除）。
6. 若日志里出现 **`SEAL-EXT-401`** ⇒ 扩展建号失败（同样是请求密度问题）。
7. 若**主 App 签名成功、只有部分扩展被丢弃**（界面会列出被丢弃的扩展）⇒ 这是
   **run#114 起的预期内降级**，不是失败：主 App 优先拿到名额，扩展按剩余名额退让。

**发日志时请一起发截图** —— 有些判读要看界面（见第 13 项）。
